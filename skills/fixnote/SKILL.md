# 糾正筆記

使用者的程式底子不強，正在學習判斷程式哪裡要改。這本筆記的目的有兩個：

1. **學習**：每一筆都附上白話解釋，讓使用者慢慢認得常見的錯誤模式。
2. **把糾正變成規定**：每一筆都要告訴使用者「寫死什麼規定，以後就不會再犯」。同樣的錯出現多次，就真的把那條規定做出來，而不是一再口頭糾正。這個想法來自 Lauren Tan 的演講〈All Code Is Slop (Except Mine)〉。

使用者只負責說「發生了什麼」，其他欄位由你補。所以要讓輸入越輕鬆越好，不要讓他覺得在填表。

筆記本位置（固定，不管目前在哪個專案、哪台電腦）：`~/.claude/fixnote/糾正筆記.md`。旁邊的「糾正筆記」面板會讀這個檔案，所以格式要照下面寫，面板才讀得懂。

## 判斷要做哪件事

- 使用者說「回顧」「整理」「看筆記」「有哪些重複的錯」→ 做下面的〈回顧〉。
- 其他情況 → 做〈記一筆〉。

## 記一筆

### 1. 收集內容

如果使用者觸發時已經寫了內容（例如 `/fixnote 按鈕點了沒反應`，或面板送來的「發生什麼事：…」），直接用，不要再問一次。

如果只打了 `/fixnote`，但從剛才的對話看得出 AI 做錯了什麼，用一句話確認就好，例如「要記的是『它改了 config.js』這件事嗎？」。對話很長時可能有好幾個錯，猜錯會記到錯的東西，所以先確認。

只有在完全不知道要記什麼時，才用這段提示問他，原樣貼出：

```
要記哪個錯？用一句話說就好，例如：
・「按儲存沒反應」
・「它改了我沒叫它改的檔案」
・「又用 setTimeout 硬等」

（選填）你原本希望它怎麼做？
（選填）在哪個專案或檔案？不寫我會自己看。
```

只有第一題是必填。使用者只回一句話也完全沒問題，不要追問選填的部分。

如果一句話裡其實有兩個不同類別的錯（例如「catch 裡什麼都不做，又加了 setTimeout」），就拆成兩筆，各自分類。合成一筆的話，其中一類的次數會被漏算，重複提醒就失效了。

這個 skill 只負責記錄。使用者如果也要你修這個錯，先記完，再照他的要求去修。

### 2. 補上其餘欄位

如果在專案裡，而且錯誤和程式碼有關，先看一下相關的程式碼或剛才的改動，讓「原因」有根據，而不是猜的。

- **分類**：從下面挑一個最接近的，標題裡**只寫粗體的類別名稱，一字不改**。次數是靠比對這個名稱算出來的，寫法不一致就會算錯。真的都不合，才自己加一個新的短名稱。
  - **功能沒做到**：結果錯誤，或說做好了其實沒作用
  - **改到不相關的地方**
  - **繞過問題**：workaround、硬等（setTimeout）、留「之後再修」的註解
  - **重複的程式碼**
  - **錯誤被吞掉**：空的 catch、出錯了卻不顯示
  - **寫死的數值或密碼**
  - **命名看不懂或函式太長**
  - **誤解需求**
  - **弄壞原本能用的功能**
- **原因**：用不懂程式的人聽得懂的話解釋，兩三句以內。如果要用術語，順便說它是什麼意思。沒看到程式碼、只能推測時，開頭寫「（推測）」。
- **預防**：下次怎麼避免，一句話。
- **防護方式**、**寫死的規定**、**防護強度**、**以後會怎樣**：見下一節。這是使用者最需要的回饋。

### 3. 防護方式：寫死什麼規定

從下面 9 種裡挑**一種**最適合的（只能用這 9 種，使用者只選了這些）。「防護方式」欄寫中文名稱。

| 防護方式 | 白話說明 | 強度 | 常對應的分類 |
|---|---|---|---|
| lint 規則 | 自動掃描程式，出現禁止的寫法就報錯 | 擋下 | 繞過問題、錯誤被吞掉、命名看不懂或函式太長 |
| 靜態分析 | 不執行程式，直接讀程式找問題，例如型別檢查、找出寫死的密碼、找重複的程式碼 | 擋下 | 寫死的數值或密碼、重複的程式碼 |
| 回歸測試 | 修好之後寫一個測試，確保這個 bug 不會再出現 | 抓到 | 弄壞原本能用的功能、功能沒做到 |
| 單元測試 | 測一個小函式：給它輸入，檢查輸出對不對 | 抓到 | 功能沒做到 |
| 功能測試 | 測一個完整功能有沒有照需求運作 | 抓到 | 功能沒做到 |
| 驗收測試 | 把使用者的需求寫成測試，檢查 AI 有沒有搞懂要做什麼 | 抓到 | 誤解需求 |
| 冒煙測試 | 最基本的檢查：程式能不能啟動、主要頁面能不能打開 | 抓到 | 弄壞原本能用的功能 |
| 畫面測試 | 讓 AI 自己操作程式並截圖，確認畫面正確 | 抓到 | 功能沒做到 |
| 變異測試 | 故意把程式改壞，看測試抓不抓得到，用來揪出 AI 寫的假測試 | 抓到 | AI 為了讓測試過而作弊 |

**強度要誠實寫**，使用者靠這個判斷安不安心：

- **擋下**：這種寫法根本過不了檢查，AI 寫了也會被要求改掉。只有 lint 規則和靜態分析做得到「不可能再犯」。
- **抓到**：AI 還是可能寫錯，但測試會失敗，錯誤不會悄悄溜過去。
- **只能提醒**：9 種都不適用、需要判斷力時才用。規定寫進專案的 CLAUDE.md，AI 通常會遵守，但不保證。這時「防護方式」寫「寫進 CLAUDE.md」。

「改到不相關的地方」這類錯通常只能提醒，除非能用 lint 規則畫出資料夾邊界（例如「A 資料夾不准 import B 資料夾」），那就是擋下。

**寫死的規定**：用一句白話寫出那條規定本身，讓不懂程式的人也看得懂，例如：
- 「程式裡不准出現 setTimeout，出現就檢查不通過。」
- 「每次修改後，都要自動確認『按儲存後重新整理，資料還在』。」

**以後會怎樣**：一句話說明加了這條規定後，下次 AI 再犯會發生什麼事，例如：
- 「AI 再寫 setTimeout，檢查會直接報錯，並告訴它要改成等資料真的載入完成。」

lint 規則的錯誤訊息要寫成「告訴 AI 怎麼修根本原因」，不要只說「禁止」。這是影片的重點：好的錯誤訊息會引導 AI 走對的路。

### 3.5 立即上鎖：讓糾正筆記 mod 當場擋下

使用者裝了「糾正筆記」mod。它會讀筆記本裡的**擋下規則**，在 Claude 寫檔（Write、Edit）之前檢查內容，符合規則就直接擋下，並把「寫死的規定」和「以後會怎樣」當成修正指示告訴 Claude。這條規定不用等專案設定 lint，**記完的那一刻就生效**，在任何專案都有效。這是使用者最想看到的效果：親眼看到同樣的錯被擋下。

只要錯誤能用「程式碼裡出現某段文字」來判斷，就寫擋下規則：

- **擋下規則**：一個 JavaScript 正規表達式，放在反引號裡，例如 `\bsetTimeout\s*\(`、`catch\s*(\([^)]*\))?\s*\{\s*\}`。
  - 要**精準**：寧可漏抓，也不要誤擋正常程式碼。誤擋會讓使用者覺得這工具很煩。
  - 不要用 `^`、`$` 以外的旗標，也不要寫成 `/.../g` 的樣子，只寫中間的內容。
- **適用檔案**：會被檢查的副檔名，用空白分隔，例如 `.ts .tsx .js .jsx`。不寫就檢查常見的程式碼檔案。Markdown 檔永遠不檢查，因為筆記本自己就寫著違規範例。
- **違規範例**：一小段會被擋下的程式碼。面板上的「試擋看看」按鈕會拿它示範擋下的效果，所以**它一定要符合擋下規則**。
- **合格範例**：一小段正確寫法，**一定不能符合擋下規則**。面板會用它證明「正確寫法不會被擋」。

寫完後自己檢查一次：違規範例符合規則、合格範例不符合。不確定的話，用 Bash 跑 `node -e` 驗證。

有擋下規則的那筆，強度寫「擋下」，狀態寫「已上鎖」。錯誤沒辦法用文字判斷（例如「誤解需求」）就不寫這四個欄位，照原本的方式寫「抓到」或「只能提醒」。

mod 只擋得住 Claude Code 裡的 AI，擋不住你自己手打的程式或其他工具。所以同類錯出現 3 次以上時，仍然建議把它做成專案的 lint 規則或測試，兩道防線一起顧。

### 4. 寫進筆記本

先讀筆記本，算出下一個編號，再把新的一筆接在檔案最後。如果檔案不存在，先建立它（包含 `~/.claude/fixnote/` 資料夾），最上面放 `# 糾正筆記`。

格式固定如下（日期用今天的日期）：

```markdown
## #編號 YYYY-MM-DD｜分類

- **發生什麼事**：使用者的原話，只修錯字
- **原本希望**：使用者有寫才放這行
- **專案／檔案**：知道才放這行
- **原因**：……
- **預防**：……
- **防護方式**：lint 規則
- **寫死的規定**：……
- **防護強度**：擋下
- **以後會怎樣**：……
- **擋下規則**：`……`
- **適用檔案**：`.ts .tsx .js .jsx`
- **違規範例**：`……`
- **合格範例**：`……`
- **狀態**：已上鎖
```

擋下規則那四行只有在能上鎖時才寫。沒有擋下規則時，狀態寫「已記錄」。

「發生什麼事」保留使用者自己的說法，因為回頭看時，他自己的話最好懂。

### 5. 檢查有沒有重複

寫完後，數一下筆記本裡和這筆**同分類**的筆數（包含剛寫的這筆）：

- 3 筆以上：明確告訴使用者「這類錯已經出現 N 次了，該把規定真的做出來了」，並問他要不要現在做。如果目前不在任何專案裡，就說明這個規定要加在哪個專案，等他打開那個專案再做。
- 少於 3 筆：不用特別提。

### 6. 回覆使用者

回覆要短，用這個格式：

```
記成第 N 筆（分類）。
原因：一句話。

🔒 寫死的規定：……
強度：擋下／抓到／只能提醒，用白話解釋這個強度代表什麼
以後：……
```

有擋下規則時，最後加一句：「🛡 已上鎖：從現在起，Claude 在任何專案寫出這種程式碼都會被當場擋下。可以在糾正筆記面板按『試擋看看』親眼確認。」

最後再加上重複提醒（如果有）。不要把整筆內容再貼一次。

## 回顧

讀整本筆記，然後回報：

1. 總共幾筆，各分類幾筆，從多到少排。
2. 出現 2 次以上的類別（最多 3 類），各用一句話說明這類錯是什麼。
3. 推薦最值得先做的 1 到 2 條規定。一條規定常常能同時顧到好幾筆（例如一條「禁止 setTimeout」的 lint 規則），所以用「規定」來分組，寫出每條規定會顧到哪幾筆、強度是什麼。優先推薦顧到最多筆、強度是「擋下」的。問使用者要不要開始做。

狀態只有四種：
- 已記錄
- 已上鎖：有擋下規則，由糾正筆記 mod 當場擋下
- 已做成規定：（簡述做了什麼，加在哪個專案）
- 不做：（簡述原因）

做完一條規定後，把它顧到的**每一筆**都改成「已做成規定」。
